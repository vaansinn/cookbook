## Already shipped

- #48 — Idempotent cook logging (commit f4af8c7), plus a reconciliation pass (commits `05b2d07`/`6c901b2`) closing the gap between what shipped and what the fixture contract actually requires. `POST /api/cook-log` had no idempotency key, so a retried request (flaky network, double-tap, bfcache resubmit) created a second `CookLog` row for one cook. `CookLog` gets a nullable `session_id` column (migration `d4435c97466d`, additive) plus a unique constraint on `(user_id, session_id)` only — narrow on purpose, so a `session_id` reused with a different dish/level is a conflict, not a second insert. `log_cook`: no `session_id` → inserts like before (back-compat); a fresh `session_id` → new row (`201 created`); an existing `session_id` with matching dish/level → the existing row, no new insert (`200 already_saved`); an existing `session_id` with a *different* dish/level → `409 conflict`, existing row untouched. The concurrent-double-submit race is closed at the DB level (unique-constraint `IntegrityError` caught, loser re-reads and replays instead of 500ing) — verified with a real forced race (two threads synchronized past the pre-check), not just reasoned about.
  The first pass only minted `session_id` via a bare component-mount `useRef` (lost on refresh) and silently navigated away on any `logCook` failure as if it had succeeded — both caught on independent review, not at merge time. Fixed: new `frontend/src/store/cookSession.js` persists the session to `localStorage`, keyed `(owner_namespace, owner_id)` — `"account"` + `user_id` for now, shaped to hold a future `"guest"` value without a key change — so a refresh mid-cook reuses the same `session_id` instead of starting a new attempt; cleared on logout/account-switch by comparing `useAuthStore`'s `prevState.user` directly (not a separately-tracked variable seeded at module-load time, which would race against `useAuthStore.init()`'s async `/auth/me` check and silently fail to clear a returning user's session on their next logout — found and fixed during merge review, verified with a targeted Playwright test). `CookMode.jsx`'s Finish button now shows a visible error + retry on a real failure, reusing the same `session_id` on retry, instead of navigating away.
  Still explicitly pending (Wave 3, not silently dropped): `CookLog` has no `lang`/`snapshot_id` columns yet, so the conflict-check compares only `(dish_id, level)`, not the fixture contract's full 4-tuple.
4/5 — the unique-constraint-plus-catch approach closes the race at the level that actually matters (the DB), and the reconciliation pass fixed two real correctness bugs the first pass's own testing missed (lost-session-on-refresh, silent-failure-as-success), one of which was itself only caught on a second independent review rather than the reconciliation agent's own verification; docked one point for needing two review passes to get the lifecycle actually right rather than one.

- #50 — Fix `frontend/public/sw.js`'s unsafe API cache and the account-switch state leak it enabled (commit f4e2276). The `API_CACHE` branch used to cache every `/api/*` GET unconditionally and replay it offline with no auth awareness — `GET /api/dishes/<slug>` included, whose content varies by tier access even though the path looks static — so one account's cached (possibly premium) response could leak to a different account on the same device/browser, including offline. Fix: any request carrying an `Authorization` header now bypasses both cache-read and cache-put entirely; only a small allowlist of genuinely public, non-entitlement-varying paths (`/api/glossary*`, `/api/dishes`, `/api/filters`) keeps the old cache-fallback behavior. Bumped `SHELL_CACHE`/`API_CACHE` to `-v2` so stale entries evict via the existing `activate` handler. Accepted regression, not a bug: a previously-viewed recipe's detail is no longer available offline. Separately, no store was reset on logout and a slow in-flight request from account A could resolve after B logged in and silently overwrite B's state — added an `epoch` counter on `useAuthStore` (bumps on login/register/logout/account-deletion, and on a 401 arriving mid-session via a new response interceptor in `api/client.js`); every fetch touching shared state (`useFavoritesStore.load/toggle`, `RecipePage`'s dish fetch, `CookMode`'s dish fetch + cook-log) now captures the epoch before the request and discards the result on both success and failure if it's changed by the time the response lands. `useFavoritesStore` also self-resets on every epoch change. Verified in a real two-account browser session (Playwright against the pre-installed headless Chromium, both the Vite dev server and the production Flask-served build): premium content clears immediately on logout without navigating away; a delayed favorites fetch started under A never lands after switching to B mid-flight; a delayed *failed* dish-fetch under A does not clobber valid content B/A-next-epoch has since rendered (confirmed with a negative control — temporarily removing the catch-side guard reproduced the clobber, restoring it fixed it); and a full A-cooks→logout→B-logs-in pass showed B's favorites/API cache empty of A's data and Advanced correctly re-locked for B. One acceptance check (a literal offline-network toggle against the running service worker) could not be driven from this headless harness — `context.setOffline`/route-level aborts don't reach the SW's own internal `fetch()` here — so that property was instead verified by inspecting the API cache's actual keys, which never included `/api/dishes/<slug>` or `/api/favorites` at any point, so an offline lookup for either could not return a leaked response.
4/5 — the epoch counter is a single shared primitive that closes the auth-header cache leak, the stale-success leak, and the stale-error-clobber leak in one mechanism instead of four bespoke patches, and the negative-control test proved it's load-bearing rather than incidental; docked one point because the fully-offline SW acceptance check had to be verified indirectly (cache-key inspection) rather than by literally flipping the network off, a gap in this environment's browser-automation tooling rather than in the fix itself.
