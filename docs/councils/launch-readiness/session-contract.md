# D01 — session and recovery decision record (proposed)

2026-10-05, base `04a414f218c909dea3c82e720d8d5ac8ba84e228`. Status: engineering recommendation for D05/security review, **not implemented or approved**. Q06's launch access and email-ownership promises remain open ([questions](implementation-questions.md#q06--accounts-and-access-at-launch)); this ADR does not change current tier or guest rules.

## Current contract and decision

**User decision update, 2026-10-05:** Q06 now approves guest Basic cooking, free
curated recipes for signed-in accounts, email verification/password recovery and
paid tiers later. Earlier pending-policy wording describes the pre-answer draft;
see the [decision register](implementation-questions.md#q06--accounts-and-access-at-launch).
Transport, migration and precise verification-state behavior remain engineering
work. Current code and premium gates were not changed when recording the answer.

Register/login return a bearer JWT; protected routes use `@jwt_required`, and optional-auth recipe/lesson/snapshot routes inspect a supplied identity ([auth.py:130](../../../routes/auth.py#L130), [recipes.py:60](../../../routes/recipes.py#L60)). JWT lifetime is 30 days and there is a current-user lookup, so a deleted user's token fails, but there is no per-session revocation ([app.py:49](../../../app.py#L49), [auth_identity.py:11](../../../auth_identity.py#L11)). The frontend keeps the token in `localStorage`, attaches it as `Authorization: Bearer`, and logout only removes that browser copy ([useAuthStore.js:9](../../../frontend/src/store/useAuthStore.js#L9), [client.js:8](../../../frontend/src/api/client.js#L8)). Cross-tab invalidation and stale-response guards exist, but a copied token stays valid until expiry or account deletion ([useAuthStore.js:72](../../../frontend/src/store/useAuthStore.js#L72)). There are no reset, verification or server logout endpoints in [auth.py](../../../routes/auth.py#L130).

| Option | Migration and revocation | Tradeoff |
|---|---|---|
| A. Keep self-contained 30-day JWTs | Minimal client change; global password/session epoch or denylist needed for early invalidation | Copied bearer remains a long-lived credential without those additions; denylist itself becomes server state |
| B. Keep bearer API; add server session ID/registry and short-lived access tokens | Add session ID to JWT, check active session on every protected and optional-auth request; add logout-all, reset and renewal. Accept old JWTs only through a finite transition window | Smallest API migration, but browser-held bearer is still accessible to script; revocation requires DB/registry availability and a designed outage response |
| C. Same-origin opaque server session in `Secure`, `HttpOnly`, `SameSite` cookie | Rework browser client and API transport; expire/rotate server record; explicitly bridge or retire old bearer clients and old assets | Removes direct token reads by app script; cookie-authenticated writes and logout need CSRF protection and strict origin policy; greater coordinated rollout |
| D. Controlled cutover to C with one-time reauthentication | Deploy upgraded client/server, reject old bearer transport from a dated cutover, require sign-in again; retain the creator account and data | Simpler revocation promise and less dual-transport code, but old tabs/assets need an enforced upgrade path and a planned interruption. The supplied launch premise is one creator account today; verify that premise before selecting this path. |

**Recommendation for engineering review: C with D as the simpler rollout if the supplied one-creator-account premise is confirmed.** The phone-first PWA is served from the same origin as `/api` ([app.py:204](../../../app.py#L204)); a server-side opaque session makes logout, reset and device-level revocation unambiguous **for upgraded clients that call the server**. The current frontend's logout only removes local storage and sends no request ([useAuthStore.js:18](../../../frontend/src/store/useAuthStore.js#L18)); its copied JWT remains valid until expiry, account deletion, a server-side global revocation event or controlled cutover. A finite dual-transport transition is justified only if old clients must keep working; it cannot provide a uniform logout promise while old local-only logout remains possible. If rollout complexity rules out C, B is a bounded fallback **only** with short access life, server lookup/revocation and documented script-access risk. No option changes creator records or tier policy by itself.

## Proposed technical contract for D05

1. Store only an opaque, high-entropy session secret in a `Secure; HttpOnly; SameSite=Lax` cookie scoped to the API/app origin; retain a server-side hashed identifier, user ID, creation/last-use, absolute/idle expiry and revocation timestamps. Rotate on login and successful recovery; provide current-device logout and all-device revocation. Decide numeric lifetimes with operational review. Every protected request resolves a **current** user and unrevoked session; unavailable session storage returns retryable 503, never a guest downgrade. For optional-auth routes, only the absence of **both** credential types is guest; an invalid supplied credential fails closed rather than silently becoming guest. Preserve the current deleted-user 401 semantics from [auth_identity.py](../../../auth_identity.py#L11).
2. Require same-origin requests, a CSRF token bound to the session for every state-changing cookie request including logout, and Origin/Referer checks as a second defense. `SameSite` is not a CSRF policy by itself. Do not enable credentialed cross-origin API access merely because the existing CORS setting permits configured origins ([app.py:57](../../../app.py#L57)). Login and reset also need CSRF or equivalent origin gating. Keep GET handlers free of mutations; `/api/grocery-list` currently creates a list on read ([groceries.py:87](../../../routes/groceries.py#L87)) and must be corrected before cookie cutover.
3. Add bounded login/register/reset/verification attempts and non-enumerating public recovery responses. Generate random single-use, short-lived reset/verification tokens; persist **hashes**, purpose, user, expiry and consumption state. Use a configured trusted origin to build links. Consume and rotate credentials atomically; failed mail handoff must leave a clear retry path. A successful password reset revokes all active server sessions and all legacy JWTs for that account; test copied old credentials and tell the user to sign in again. Never place a reset token in ordinary logs, URLs returned to unrelated users, or a long-lived browser store. Existing password hash semantics for old accounts must remain verifiable ([auth.py:76](../../../routes/auth.py#L76)).
4. **If dual transport is selected:** accept one credential transport per request. Cookie present means validate that cookie; a rejected/expired cookie returns 401 (or 503 on store outage) and must **never** fall back to an `Authorization` bearer. If cookie and bearer are both present, reject as ambiguous before route work, even if either looks valid; an upgraded client clears its old browser token and retries with one transport. Only when no cookie is present may a pre-cutover bearer be considered. Apply the same rule to optional-auth content and every legacy endpoint. An old tab sharing a browser with a new cookie login may receive an auth error; existing old-client UI behavior is unverified, so do not promise that it shows an upgrade notice.
5. **Legacy revocation in a dual transition:** record a per-user legacy-token cutoff or generation and check each old token's signed issue time/identity against it on every request, as well as normal signature/expiry/current-user checks. Stop minting legacy tokens at the chosen cutover; refuse tokens without the claims needed to enforce revocation, or use a tested equivalent denylist. A successful **upgraded-client server logout**, password reset, account deletion or all-device revocation must atomically invalidate previously issued legacy JWTs for that account before reporting success; current-device cookie logout also revokes its server session. The **old frontend's local-only logout cannot trigger this server revocation** and must not be described as doing so. Test clock granularity and races so a token issued at the cutoff instant cannot pass. A DB outage must fail closed with retryable 503 rather than bypass this check.
6. **Migration choice:** D uses additive session storage, upgraded cookie/CSRF frontend and server, then one-time reauthentication at a dated enforced bearer retirement; preserve creator records and verify old tabs fail closed. If a finite dual transition is chosen instead, add the precedence and legacy revocation checks above, observe old-client usage without logging credentials, and specify that old local logout leaves a copied JWT usable until expiry or a server-side invalidation. To promise uniform server logout, enforce upgrade/retirement of the old client rather than merely waiting for the window to end. Test a previous shipped client and recovery build against candidate-created records; align with D04's proposed [release-runbook.md](release-runbook.md). Do not delete or re-create existing creator accounts to switch transport.

## User-visible consequences and open Q06

Guest Basic cooking and current tier gates remain as implemented until Q06 decides first-release access. Q06 must settle whether accounts are optional beyond guest cooking, which features require verified email (especially invitations), the recovery and session-expiry promise, and whether existing premium access needs a commercial path while paid tiers are deferred. Public sign-up and later Stripe intent are recorded, but verification, recovery and access consequences are not fully answered ([implementation-questions.md:71](implementation-questions.md#q06--accounts-and-access-at-launch)). The engineer can settle cookie/CSRF/session mechanics after review; the user chooses the access promise. If mail is unavailable at launch, do not silently advertise self-service recovery/verification.

## Synthetic acceptance specification (not run)

- Anonymous: protected `/api/auth/me`, private planning and shared household writes return 401 with no data or write; guest Basic content remains reachable; a malformed supplied session on optional-auth content does not inherit guest access.
- Cross-account: session A cannot read B's export, private IDs or mutation receipt; changing the browser account while an old response is in flight cannot hydrate A's data under B.
- Dual transport, if chosen: cookie A plus bearer B rejects without choosing either account; malformed/expired cookie plus valid legacy bearer rejects without fallback; cookie absent plus valid eligible old bearer works only inside the window; optional-auth content obeys the same rule. A new client clears its stored bearer before cookie use. Record the actual old-tab response/UI; no upgrade notification exists in the current old client.
- Logout/reset/deleted owner: after an **upgraded client's successful server logout** or a successful reset, copied cookies and old JWTs for that user fail, including on another tab/device and during any transition. By contrast, old-client local logout sends no server request: a copied old JWT remains accepted within a dual window until expiry or separate server invalidation. Under D's enforced cutover, it fails from the retirement time. Deleted account fails even from an old browser. DB outage returns 503; race and cutoff-boundary requests cannot regain access.
- CSRF: cross-origin form/fetch and absent/wrong token reject every cookie-authenticated write, including legacy endpoints and logout; valid same-origin write succeeds. Test both old bearer and new cookie clients during transition, including two open tabs and installed PWA restart.
- Recovery: unknown email response matches known email, token expires and is single-use under concurrent redemption, reset failures roll back credential/session changes, verification cannot be replayed. Fake mail only; no external provider access in D01.

Existing `test_auth_identity.py`, `test_auth_validation.py`, `tests/frontend/test_auth_recovery.mjs`, and `test_account_copy.mjs` cover pieces of current identity/client behavior; they do **not** prove this proposed session/recovery contract. No suite or browser was run for this ADR.
