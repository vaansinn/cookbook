# D04 disposable PostgreSQL recovery test design

Status: **PROPOSED test specification; not run or implemented**. Companion to [release-runbook.md](release-runbook.md). A prior current-build five-database CI rehearsal passed on 2026-09-18 (run 35339011776, inspected 2026-10-05); it was not rerun today. Its [`verify_release.py`](../../../scripts/verify_release.py) stage list (lines 58-66) includes a current-build restore. [`verify_planning_restore.py`](../../../scripts/verify_planning_restore.py) lines 320-413 loads the same source tree for restored reads/writes and expressly disclaims an old-backend recovery test. The new proof below is required before claiming a compatible recovery path.

## Artifact and target admission

1. Select an immutable **candidate** artifact `C` (code, content tree, static manifest, dependency resolution and migration head) and an independently built **designated recovery** artifact `R`. Record SHA-256 digests and the source commit for each. `R` may be a purpose-built bridge binary; calling the previous production artifact “rollback” does not make it compatible. Reject a changed or unreproducible artifact. Never build `R` from the live working directory halfway through the test.
2. Coordinator reserves one exclusive, bounded local PostgreSQL 16 cluster, loopback-only, disposable credentials and a unique run identity. Assign exactly five new empty database names from a fixed allowlist within that cluster: `control_source` (baseline), `candidate_source` (successful candidate and archive source), `failure_source` (late failure and controlled rerun), `recovery_restore` (designated build read/write), `deletion_replay` (older archive plus post-archive decisions). These are proposed names; the implementation may use fixed `cookbook_test_*` equivalents, but must enumerate every target and URL key in code before admission. Separate them from the five existing release-verifier targets and from all occupied PG09/PG10 targets. Do not point to `DATABASE_URL`, a saved local database or a shared CI cluster. The test script must take only explicit test URL keys and confirmation, sanitize inherited environment/dotenv, verify server address/port/database/role/major version, then inspect **all five targets read-only for emptiness** before importing app code or issuing a migration/fixture. If any exists with objects or identity differs, refuse with no writes. No reset, drop, `--clean`, inferred next target or automatic retry. Bound process/lock/statement timeouts; on timeout verify every child has stopped and retain targets/logs for diagnosis.
3. Provision fresh names only inside the verified job-owned cluster, then run all steps serially under one coordinator lock. Keep source and restored targets occupied at completion or failure for review. Cleanup is a separate exact-identity action after evidence is accepted, never a script fallback. Existing CI provisions a job-owned tmpfs cluster and checks container identity before removal ([`verify.yml`](../../../.github/workflows/verify.yml) lines 66-118); a new test must preserve at least that admission discipline. The existing release runner's guard and no-resume behavior are in [`verify_release.py`](../../../scripts/verify_release.py) lines 1-32, 73-102, 145-153 and 216-235.

## Scenario and assertions

| Stage | Synthetic operation | Required evidence |
| --- | --- | --- |
| A. Baseline | Migrate `control_source` to predecessor head, seed three distinct users: A for deletion, B for a revoked session while the account survives, and C for the global legacy-JWT cutoff. Include a retained creator record, private plan/event/shopping state, legacy shared row, immutable cook snapshot and catalog revision. Capture a pre-archive old bearer for each user and a prior asset/client manifest. Snapshot rows, IDs, constraints, sequences, digests and timestamps. Prepare a synthetic external decision ledger for later deletion, link/catalog revocation, session invalidation and legacy-JWT cutoff; do not pretend the current app writes one. | Ownership and creator attribution are explicit; no production data. Identify old-format receipts and the exact prior client/session transport. |
| B. Candidate | Restore/copy the admitted baseline into empty `candidate_source`, apply candidate migrations and complete a successful staged candidate content publication. Create **candidate-format** planning/event/shopping records: configured catalog revision, selected options/servings, projection/coverage/extras/preferences/template, successful mutation receipts, removal preview/undo and a current cook snapshot. Use two accounts to expose cross-account leaks. Perform candidate-format create/edit/delete and retry with the same mutation ID; record exact status/body, revision, IDs and post-write snapshot. | Candidate schema/head, catalog digest and receipt replay match. Existing creator/legacy records remain as expected; new records really use candidate fields, not just old fixtures. [`routes/planning.py`](../../../routes/planning.py) lines 340-419 is the current receipt/transaction boundary. |
| C. Late sync failure | Restore/copy the admitted baseline into separate empty `failure_source`. From `C`, run migration then recipe → glossary → skill → lesson stages. Inject a deterministic failure **after candidate content writes but before the single coordinated commit or staged activation**, preferably at the last lesson/dependency boundary; capture stage marker and all database snapshots. The chosen implementation must test its actual commit/activation failure boundary on this target without resetting it. Any genuinely independent second fault scenario requires a separately named, empty, pre-admitted target and an updated allowlist before the run; it is outside this five-target scenario. | No partially validated new revision is eligible for normal reads; previously published revisions and old snapshots remain intact. A coordinated transaction must roll back its content writes; staged activation must leave the old pointer active. Actual committed state and visibility agree. A failed rerun with unchanged artifact makes no extra rows/receipts or reopens revoked content. Any visibility breach fails the design, rather than being waived because the command exited nonzero. Current `Procfile` plus separate commits cannot satisfy this without D12 changes ([`Procfile`](../../../Procfile) line 2; [`sync_learning.py`](../../../scripts/sync_learning.py) lines 150-230). |
| D. Recovery point | Save a custom-format archive from the **occupied candidate-format source** only after recording an exact immutable snapshot. Restore with `pg_restore --exit-on-error --single-transaction` into independently verified empty `recovery_restore`, no `--clean` or `--create`. Compare complete public table rows, schema, constraints/indexes and sequence state; keep source unchanged. | Archive identity, duration and hashes recorded. Reuse the comparison model in [`verify_planning_restore.py`](../../../scripts/verify_planning_restore.py) lines 183-229; a schema-only or SQLite clone is insufficient. |
| E. Designated `R` | Launch `R` against `recovery_restore` with sanitized test configuration. Read candidate-created plan/event/shopping/configured preview and cook snapshot; read current export for owner; deny cross-account access; reject revoked/unpublished catalog selection and expired undo/preview. Replay old and candidate receipt envelopes exactly. Then perform a **new** plan edit and shopping/template command through `R`, retry both, and verify one revision advance and one side effect each. Exercise the previous client and a copied old bearer during any declared dual-transport window; an invalid supplied credential must not downgrade to guest. | `R` must successfully **read and write** the restored candidate format and honor the selected session compatibility contract. Confirm exact response/replay and post-write row/sequence/receipt state. A startup check, `SELECT 1`, read-only export or `R` running its own migration is not enough. If `R` cannot interpret a new receipt or enforce the declared old-bearer boundary, fail admission and choose a different recovery build/forward repair. |
| F. Deletion/revocation | **After the archive point** in `candidate_source`, delete A, revoke a named-plan link/catalog revision and remove a household member while retaining Q07-approved shared rows. Revoke B's captured bearer/session but keep B's account live. End legacy-JWT acceptance after C's old bearer was issued, with C's account still live and otherwise authorized. Restore the older Stage D archive into the separately admitted empty fifth target, `deletion_replay`, then replay the external deletion/revocation/session-invalidation decisions and the durable legacy-JWT cutoff before accepting traffic. Sign in as B through `R` **on that restored target** to create the valid-session control; a post-archive session from the source is not assumed to exist in the restored database. Request protected and optional-auth routes with A's, B's and C's copied old bearers, B's newly issued restored-target credential and any relevant cookie; inspect cross-account/shared data, deleted/revoked references and exports. | A's old bearer returns 401 even though the archive contained A's user row; replay has removed it. B's specifically revoked credential returns 401 while B's new restored-target session works; C's otherwise valid legacy JWT returns 401 after the cutoff. None may fall back to guest on optional-auth routes. Recovery build `R` must enforce the cutoff at least as strictly as the candidate: an older artifact that resumes accepting legacy JWTs fails admission. Prevent restored/reused subject IDs from granting bearer access. Deleted data and revoked content/link stay unavailable; shared/creator records follow approved Q07 without invented attribution. This tests continuity across backup age, not just current application `DELETE /api/auth/me` ([`routes/auth.py`](../../../routes/auth.py) lines 239-284; [`auth_identity.py`](../../../auth_identity.py) lines 11-35). Link/session revocation, cutoff persistence, journal and policy are **proposed**, not current capabilities; this stage is blocked until implemented. |
| G. Controlled rerun | Against retained `failure_source`, use the *same pinned* `C` only after a read-only head/content/marker/availability comparison and explicit run admission. Rerun serially under the lock; repeat receipts, revoked-content and creator checks. Separately demonstrate that a changed content digest or unexpected populated target refuses without writes. | Complete publication becomes visible only once, unchanged revisions do not overwrite revocation, existing records survive, and the mismatch path stops safely. Never feed an occupied verifier target to the present `verify_release.py`, which intentionally refuses it. |

The fixture needs both pre-existing and candidate-format rows. Current `planning_catalog.py` lines 247-300 preserves a revoked revision on matching replay, but the publication mechanism is not in the release chain. Current named-plan public links have no explicit expiry/revocation path ([`legacy-contract.md`](legacy-contract.md#current-record-and-access-facts)); Stage F uses the **proposed** Q07 link lifecycle, not a claimed current route. Current account deletion clears attribution on retained household rows ([`routes/auth.py`](../../../routes/auth.py) lines 262-280); Q07 must settle whether that is the approved final behavior. [D02's PX09 evidence](parity-evidence.md) requires separate legacy and private IDs; do not fabricate an alias or provenance during this restore. [D01's session ADR](session-contract.md#current-contract-and-decision) confirms copied old bearers currently lack logout/reset revocation, so Stage F cannot pass on today's code. Do not interpret test success as legal approval.

## Evidence and implementation boundary

- Record a compact, redacted run ledger: cluster/run identity, all five admitted target names, exclusive owner, `C` and `R` digests, migration heads, content/commit-or-activation digests, fault-injection stage, archive checksum, old/new asset manifests, stage timestamps, rows/sequence equality result, session and old-bearer outcomes, exact receipt status/body comparisons stored in restricted test artifacts, and cleanup decision. Avoid secrets and user payloads in normal console output. Fail on any missing stage. No release approval follows automatically.
- Measure recovery interval from failure detection through writer fence, restore, journal replay, `R` activation and final read/write validation; measure archive age and unapplied candidate writes/deletion decisions. Present those observations to the operator for RTO/RPO and cost choices. No invented numerical objective appears in this design.
- Backend owns sync transaction/publication changes in `scripts/sync_recipes.py`, `scripts/sync_glossary.py`, `scripts/sync_learning.py`, `planning_catalog.py`, `app.py` and any new migration. A guarded new rehearsal script under `scripts/` and focused tests under `tests/backend/` should implement this design after D01/D07 contracts and Q07/Q10 decisions. The CI/runner owner may serialize it after existing checks; D04 changes no runner, CI, application or test source. D13 owns old-client/asset and active-cook browser checks, not this PostgreSQL proof.
