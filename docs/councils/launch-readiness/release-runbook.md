## Proposed admission and release sequence

The following is a design for a later authorized release, **not a command to run now**. Keep an evidence ledger with owner, UTC time, artifact digest, decision and result for every gate. Redact connection strings, tokens and row payloads from routine logs.

1. **Name the release**: immutable source commit, content tree hash, migration head, frontend build manifest and per-file digests, resolved Python/Node dependencies, PostgreSQL major version, candidate and designated recovery artifact digests, and the operator/approver. Build once in an isolated directory; verify that the API code, `static` output and content files in the same promoted artifact match the ledger. A passing earlier CI run is baseline evidence only; obtain candidate-specific checks.
2. **Gate policy and environment**: signed-off authored EN/DE content and images; D01 ownership/legacy access decision; Q07 shared-data/deletion and public-link policy; retention/backup policy; operator, budget, domain, mail/support and alert destinations; capacity result; exact client compatibility window; separate Q14 deployment/cutover approval. Verify target identity and permissions out of band. Do not substitute a health response for these gates. Preserve existing creator and shared records; compare representative populated history before migration. No fresh seed, cleanup, or schema downgrade against those records.
3. **Preflight locally**: reserve an exclusive disposable PostgreSQL cluster and fresh targets; inspect target identity and emptiness read-only before any fixture. Run candidate tests and the existing guarded rehearsal only when its targets are newly admitted and no other worker owns them. Rehearse the specific recovery design in [recovery-test-design.md](recovery-test-design.md). Retain occupied targets after any failure for diagnosis. Check a restorable backup from a representative synthetic populated state and record elapsed dump, restore, validation and service-recovery times.
4. **Stage publication**: place immutable candidate and recovery artifacts plus the previous client assets where the approved runtime can address them. Record their hashes. Keep previous hashed JS/CSS and fonts reachable for the agreed old-client window; do not empty the *served* asset directory during promotion. Hold a previous tab/active cook through the update, including network interruption and return. Confirm its API requests remain compatible or show an explicit safe upgrade state.
5. **Serialize writes**: one operator owns the release lock. Quiesce or bound application writes according to the tested migration contract. Take and verify a pre-change recovery point; record its time. Apply only the reviewed forward migration against the identified target, then validate and apply recipe → glossary → skill → lesson content from that same identified artifact. Record one complete-content commit/activation and its fingerprint. Readers must see either the prior complete set on failure or the fully validated candidate after success, never an intermediate mixture. Backend D12 may achieve this with a coordinated transaction plus serialization or a staged activation mechanism; its test must prove the chosen boundary, including legacy and private catalog reads. Current separate CLI commits cannot provide that guarantee. Never run two release/sync jobs concurrently, and do not let a web process silently run an extra sync.
6. **Promote and observe**: switch the approved runtime to the exact staged artifact only after migration/content readiness, then check schema/content identity, readiness, real authorized EN/DE recipe and planning/event/shopping read/write/receipt paths, old-client behavior and unauthenticated denial. Keep evidence of the checks and a known-good recovery path. Start the agreed observation window and support/alert routing. Release status is an operator decision, not inferred from `200 /health/ready`.

## Failure, rerun and recovery decisions (proposed)

- **Failure before any database write:** stop promotion; retain candidate artifacts/logs and inspect the cause. A rerun needs the same identity and fresh admission.
- **Migration or late content sync failure:** stop *all* further sync and web promotion; fence competing writers; record the exact migration head, transaction/activation outcome, row/content digests and error stage without private payloads. Current separate sync commits may already be visible. Do not blindly rerun `Procfile` or restore an older backup over new writes. Under the implemented coordinated transaction, prove rollback left the prior complete content set; under staged activation, prove the pointer stayed on that set. Otherwise treat partial content as an incident: restrict affected reads/writes as the tested mechanism permits, assess exposed records and choose a reviewed forward repair or isolated restore/replay. A same-content rerun is allowed only after verifying unchanged artifact/content hashes, target head, actual committed state, revocations and owner approval; the current upsert syncs have no complete publication/replay guarantee.
- **Failure after clients write candidate-format data:** prefer the designated *compatible recovery build* only if its test proves it can read **and write** the exact candidate schema/records, including receipts and unavailable content. An old code artifact or migration downgrade is not a rollback by default. If no compatible build is admitted, stop writes and use reviewed forward repair. Restore a backup only into an isolated empty target first, validate it, reconcile writes after the recovery point, and replay deletion/revocation **and session invalidation** decisions before any cutover. A copied old bearer remains valid under the current design until expiry or account deletion ([`session-contract.md`](session-contract.md#current-contract-and-decision)); a restored deleted user or pre-reset credential could therefore regain access without a new revocation mechanism. A still-live account's revoked session must also remain revoked after restore. A dated legacy-JWT acceptance cutoff must be durable outside the older snapshot or enforced by an admitted recovery artifact, so rollback cannot reopen that transport. Test both through the declared transition window; fail the recovery gate if logout/reset/deletion or cutoff promises cannot be enforced. Never resurrect a deleted account, revoked link/catalog revision, expired token or invalidated session merely because it existed in a backup.
- **Old clients/assets:** preserve the previous asset manifest for the chosen window; monitor 404s for old hashed assets and incompatible API calls. The current worker's cache cleanup cannot replace server-side asset retention. Do not force worker activation during a live cook. End the window only after observed client compatibility and a documented support path for long-idle clients.

## Backups, deletion continuity, alerts and support (proposed)

- Back up the database and any separately stored owned assets as one recoverable version set. Record point-in-time coverage, encryption/access controls, retention and restore instructions only after the operator chooses them. Test an isolated restore with schema, row/sequence, ownership, receipt and catalog-digest comparison. Keep durable deletion/revocation/session-invalidation decisions and any legacy-JWT cutoff **outside the recoverable snapshot**, or use an equivalent independently enforced mechanism, so restoring an older archive cannot undo them. Its access, retention and privacy policy are unresolved. The current `/api/auth/me/export` and `DELETE /api/auth/me` paths exist ([`routes/auth.py`](../../../routes/auth.py) lines 195-284), but they do not establish backup erasure or a deletion-replay journal; shared rows are retained for remaining members with attribution cleared. Do not claim GDPR compliance from the route labels.
- Alert candidates: readiness failure (separate from liveness), elevated API errors/latency, release/migration/sync stage failure, restore/backup verification failure, repeated old-asset 404s, receipt/revision conflicts beyond expected retries, and unexpected unavailable-content exposure. Decide thresholds from D11 measurements and actual traffic; test delivery and named acknowledgement. The responder records incident start, affected build/content/schema and last known safe write, fences publication if needed, contacts the named operator, follows the tested recovery branch, validates private account isolation and reports resolution. Avoid logging secrets or personal data.
- Q04/Q11/Q12 remain open for provider/topology, operating cost, backup retention, alert/support owner, and acceptable recovery time/data loss. Propose measuring backup age at failure, restore duration, validation duration, compatible-build activation duration, and unreplayed writes/deletions in the D12 rehearsal. Convert those observations and user choices into RTO/RPO targets later; **no SLO or cost is asserted here**.
